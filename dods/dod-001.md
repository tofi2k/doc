# Definitions of Done (DoD)

This document defines **binding Definitions of Done** for the Hostingmaster MVP related to **provider plugins, provider accounts, pricing, and provisioning workflows**.

The DoD ensures architectural consistency, auditability, and future extensibility. All items marked *binding* are mandatory for acceptance.

---

## DoD-001: Provider Plugin Acceptance (Binding)

A provider plugin is considered **accepted** only if all of the following criteria are met:

### Identity & Metadata

* [ ] A globally unique `pluginId` is defined.
* [ ] Plugin versioning follows semantic versioning.
* [ ] Plugin metadata documents provider-specific limitations and quirks.

### Capabilities (Binding)

* [ ] All supported capabilities are **explicitly declared**.
* [ ] Unsupported capabilities are explicitly absent and treated as valid.
* [ ] Capabilities are immutable for a given plugin version.

### Provisioning Model (Binding)

* [ ] All mutating operations return an **OperationRef**.
* [ ] No synchronous provisioning success is assumed.
* [ ] Operation states are deterministic and enumerable.

### Error Semantics (Binding)

* [ ] Errors are classified (temporary / permanent / not_supported / auth / rate_limited).
* [ ] Retryable vs. non-retryable errors are explicitly marked.
* [ ] Provider-specific error codes are preserved where safe.

### Security (Binding)

* [ ] Plugins do not persist provider credentials.
* [ ] Plugins do not log secrets or sensitive provider data.
* [ ] Plugins operate strictly within the assigned ProviderAccount scope.

---

## DoD-002: Provider Account Usability (Binding)

A ProviderAccount is considered **usable** only if:

### Ownership & Scope

* [ ] ProviderAccount is owned by exactly one reseller.
* [ ] ProviderAccount references a single ProviderPlugin.
* [ ] ProviderAccount defines its credential mode (`OWN` or `INHERIT_PARENT`).

### Inheritance Rules (Binding)

* [ ] Credential inheritance is reference-based (no copying).
* [ ] Revocation or suspension at parent level affects all descendants.
* [ ] Inheritance behavior is deterministic and auditable.

### Isolation (Binding)

* [ ] ProviderAccounts cannot be accessed across reseller boundaries.
* [ ] Customer-level provider accounts are not supported in MVP.

---

## DoD-003: Pricing Import & Resolution (Binding)

Pricing is considered **correct and complete** only if:

### Pricing Import

* [ ] Plugins import only **raw provider base prices**.
* [ ] Pricing sources may be API, CSV, or manual import.
* [ ] Missing provider pricing is supported.

### Pricing Resolution (Binding)

* [ ] Final prices are computed exclusively in the core.
* [ ] Pricing resolution order is deterministic:

  1. Included benefits (hosting plans)
  2. Explicit price overrides
  3. Derived pricing rules (markup / markdown)
  4. Inheritance from parent reseller
  5. Provider base price fallback

### Auditability (Binding)

* [ ] Each resolved price can be traced back to its rule chain.
* [ ] Pricing decisions are reproducible.

---

## DoD-004: Provisioning Workflows (Binding)

A provisioning workflow is considered **done** only if:

### Lifecycle Management

* [ ] Explicit lifecycle states are defined and persisted.
* [ ] Failed operations are distinguishable from pending ones.
* [ ] Manual intervention points are representable.

### Resilience (Binding)

* [ ] Provider outages do not block order creation.
* [ ] Retries respect provider rate limits.
* [ ] Permanent failures are surfaced clearly.

---

## DoD-005: Capability Gating & UX Consistency (Binding)

Feature exposure is considered **correct** only if:

* [ ] UI features are gated strictly by plugin capabilities.
* [ ] Unsupported actions are not silently hidden.
* [ ] Attempting unsupported actions fails explicitly.

---

## DoD-006: Architecture & Documentation (Binding)

Architecture work is considered **complete** only if:

* [ ] arc42 documentation reflects the current architecture.
* [ ] All binding ADRs are present and referenced.
* [ ] Deviations are explicitly documented.

---

## DoD-007: MVP Compliance

An MVP release is considered **architecturally valid** only if:

* [ ] No architectural shortcuts violate accepted ADRs.
* [ ] Temporary MVP deviations are explicitly documented.
* [ ] Future extensions do not require refactoring of the plugin boundary.

---

**End of Definitions of Done**
