# Definitions of Done (DoD)

This document defines **binding Definitions of Done** for the Hostingmaster MVP related to **provider plugins, provider accounts, pricing, provisioning workflows, operations, and tenant isolation**.

The DoD is intentionally **explicit and exhaustive**. Each checkbox represents a **reviewable acceptance criterion**.
If any binding item is unchecked, the implementation is **not acceptable**, even if it is functionally working.

> **Aligned ADRs:** ADR-0001 … ADR-0013 (incl. patches)

---

## DoD-001: Provider Plugin Acceptance (Binding)

A provider plugin is considered **accepted** only if **all** items below are fulfilled.

### Identity & Metadata
- [ ] A globally unique `pluginId` is defined and documented
- [ ] Plugin versioning follows semantic versioning (MAJOR.MINOR.PATCH)
- [ ] Plugin metadata documents provider-specific limitations and quirks
- [ ] Supported products (domains / SSL) are explicitly described

### Runtime Isolation (Binding)
- [ ] Plugin runs in a **process-isolated runtime** (sidecar or standalone service)
- [ ] In-process execution inside the core is explicitly forbidden
- [ ] Plugin failure (panic, OOM, crash) cannot crash the core

### Capability Declaration (Binding)
- [ ] Capabilities follow the **structured capability schema** (ADR-0005)
- [ ] Capabilities define **operations**, **coverage strategy**, and **constraints**
- [ ] Domain capability declares supported operations (register, renew, delete, update_nameservers, dnssec_enable, transfer as applicable)
- [ ] SSL capability declares supported validation types (DV/OV/EV) and product constraints (wildcard, max SANs)
- [ ] Capability coverage uses rules or catalogs, **never large enumerations** (e.g. full TLD lists)
- [ ] Capability constraints are machine-readable and deterministic
- [ ] Capabilities are immutable for a given plugin version

### Capability Enforcement (Binding)
- [ ] Unsupported operations are rejected **before execution**
- [ ] Unsupported products/constraints (e.g. SSL type, registration period) are rejected pre-flight
- [ ] Capability violations never reach the provider API
- [ ] Reaching `not_supported` at runtime is treated as a bug

### Provisioning Model (Binding)
- [ ] All mutating actions return an **OperationRef**
- [ ] No synchronous provisioning success is assumed
- [ ] Operations are permanently pinned to the plugin version that created them
- [ ] Operations are idempotent via request / idempotency keys

### Error Semantics (Binding)
- [ ] Errors are classified (temporary / permanent / not_supported / auth_failed / rate_limited / invalid_request / provider_unavailable)
- [ ] Retryable vs. non-retryable errors are explicitly marked
- [ ] Error codes imply deterministic core behavior (ADR-0008)
- [ ] Provider-specific error codes are preserved where safe
- [ ] `not_supported` errors must never occur if gating is correct

### Security (Binding)
- [ ] Plugins never persist provider credentials
- [ ] Plugins never log secrets or sensitive provider data
- [ ] Plugins operate strictly within the assigned ProviderAccount scope
- [ ] Provider credentials are accessed only via references

### Versioning (Binding)
- [ ] Operations are pinned to the plugin version that created them
- [ ] Plugin supports active + draining version semantics (ADR-0011)

## DoD-002: Provider Account Usability & Inheritance (Binding)

A ProviderAccount is considered **usable** only if **all** criteria below are met.

### Ownership & Scope
- [ ] ProviderAccount belongs to exactly one reseller
- [ ] ProviderAccount references exactly one ProviderPlugin
- [ ] ProviderAccounts cannot be accessed across reseller boundaries
- [ ] Customer-level provider accounts are not supported in MVP

### Credential Mode & Inheritance (Binding)
- [ ] Credential mode is explicit (`OWN` or `INHERIT_PARENT`)
- [ ] Credential inheritance is reference-based, never copied
- [ ] Revocation or suspension at parent level affects all descendants
- [ ] Inheritance behavior is deterministic and auditable
- [ ] Automatic credential fallback is forbidden

### Credential Versioning (Binding)
- [ ] ProviderAccount maintains a monotonically increasing `credentialsVersion`
- [ ] Each operation records `credentialsVersionUsed`
- [ ] Credential rotation increments `credentialsVersion`

### Revocation & Suspension Semantics (Binding)
- [ ] Revocation blocks **all new operations** immediately
- [ ] In-flight operations react deterministically to auth failures (ADR-0010)

## DoD-003: Pricing Import, Snapshot & Resolution (Binding)

Pricing is considered **correct and complete** only if **all** items below are satisfied.

### Pricing Import
- [ ] Plugins import **raw provider base prices only**
- [ ] Pricing sources may be API, CSV, or manual import
- [ ] Missing provider pricing is supported

### Pricing Snapshot (Binding)
- [ ] A **PriceSnapshot** is created at order submission time (ADR-0009)
- [ ] Snapshot includes all pricing inputs (provider base price, overrides, rules, benefits)
- [ ] Snapshot records all relevant version identifiers (e.g. priceListVersion, benefitsVersion)
- [ ] Provisioning uses the snapshot, not live pricing data

### Pricing Resolution Order (Binding)
- [ ] Resolution order is deterministic:
  1. Included benefits (hosting plans)
  2. Explicit price overrides
  3. Derived pricing rules (markup / markdown)
  4. Inheritance from parent reseller
  5. Provider base price fallback

### Auditability (Binding)
- [ ] Each resolved price is reproducible
- [ ] The applied rule chain is fully traceable

## DoD-004: Provisioning Workflows & Operations (Binding)

Provisioning is accepted only if **all** criteria below are fulfilled.

### Lifecycle Management
- [ ] Explicit lifecycle states are defined and persisted
- [ ] Failed operations are distinguishable from pending ones
- [ ] Manual intervention points are representable

### Operation Model (Binding)
- [ ] Operations follow the generic state machine defined in ADR-0007
- [ ] Provider-specific states are explicitly mapped to generic states
- [ ] Operations can transition to `stuck` by timeout policy (ADR-0008)
- [ ] Inconsistent states transition to `needs_reconciliation` (ADR-0013)

### Polling & Retry (Binding)
- [ ] Polling is scheduler-driven, not per-request
- [ ] Exponential backoff with jitter is applied (ADR-0008)
- [ ] Provider concurrency limits are enforced
- [ ] Provider rate limits are respected (incl. retry-after where available)
- [ ] Provider outages do not block order creation
- [ ] Permanent failures are surfaced clearly

### Reconciliation (Binding)
- [ ] Reconciliation is explicit and observable
- [ ] Compensating actions are modeled as new operations (ADR-0013)

---

## DoD-005: Capability Gating & UX Consistency (Binding)

Feature exposure is considered **correct** only if:

- [ ] UI features are gated strictly by declared capabilities
- [ ] Capability constraints are validated before execution
- [ ] Unsupported actions fail explicitly and predictably
- [ ] UI never offers actions that will deterministically fail

---

## DoD-006: Multi-Tenancy & Security (Binding)

Isolation is accepted only if **all** criteria below are met.

- [ ] All data access requires an explicit TenantContext (ADR-0012)
- [ ] Tenant filtering is enforced at the persistence layer
- [ ] No unscoped database access exists
- [ ] Cross-tenant access is technically impossible

---

## DoD-007: Architecture & Documentation Consistency (Binding)

Architecture work is complete only if:

- [ ] arc42 documentation reflects the current architecture
- [ ] arc42 explicitly references **all binding ADRs (0001–0013)**
- [ ] All binding ADRs are present and referenced
- [ ] No implementation bypasses the Provider Integration Boundary
- [ ] Deviations are explicitly documented

---

## DoD-008: MVP Compliance Gate

The MVP is considered architecturally valid only if:

- [ ] No shortcut violates any binding ADR or DoD item
- [ ] All async, pricing, and isolation guarantees hold under failure
- [ ] Temporary MVP deviations are explicitly documented
- [ ] Future extensions do not require refactoring the plugin boundary
